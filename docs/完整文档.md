## 1. 项目概述

### 1.1 项目定位

CI/CD 流水线自动搭建平台是一款面向 DevOps 团队的**零门槛**自动化工具，实现「**一键生成配置 + 一键自动部署**」的完整闭环。用户只需通过 Web 界面填写项目基本信息（仓库地址、项目类型、目标服务器等），平台即可自动生成完整的 CI/CD 配置文件并推送部署到目标环境。

### 1.2 解决的核心痛点

| 痛点 | 传统方式 | 本平台方案 |
|------|---------|-----------|
| CI/CD 配置编写门槛高 | 需熟悉 Jenkinsfile / GitLab CI / GitHub Actions 等多种 DSL | 表单填写，自动生成 |
| 多工具切换成本高 | 每个 CI/CD 工具需单独学习 | 统一界面，支持 7 种工具一键切换 |
| 跨云/隔离网络部署复杂 | 手动配置中继、堡垒机穿透 | 内置多跳网络链路支持 |
| 服务器环境初始化繁琐 | SSH 登录后手动安装 JDK/Docker/Nginx | 自动化远程环境准备 |
| 多环境/多分支管理混乱 | 各环境配置散落，易出错 | 统一环境模型 + 集成测试模式 |

### 1.3 覆盖范围

- **7 种 CI/CD 工具**：Jenkins、GitHub Actions、GitLab CI、阿里云效 DevOps、华为云 CodeArts、腾讯云 CODING、GitLab Runner（自托管）
- **6 种项目类型**：Java Maven、Java Gradle、Node.js、Python、Go、PHP
- **3 种部署模式**：Docker 容器化部署、直接部署（含产物构建/纯代码/代码+依赖）、应用服务器部署
- **3 种部署架构**：独立服务器部署、云托管部署、负载均衡集群部署

## 2. 架构设计

### 2.1 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                      前端（Vue 3 + Vite）                     │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────┐ │
│  │ 项目配置 │ │ 工具选择  │ │ 服务器配置│ │ 网络/环境/LB 配置 │ │
│  └────┬────┘ └────┬─────┘ └────┬─────┘ └───────┬──────────┘ │
│       └───────────┴────────────┴───────────────┘             │
│                           │ HTTP / WebSocket                  │
└───────────────────────────┼──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                 后端（FastAPI + Pydantic）                     │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────────────┐ │
│  │   API 路由    │  │ 配置模型校验  │  │ 凭据内存存储       │ │
│  │  /api/generate│  │ PipelineConfig│ │ CredentialStore    │ │
│  │  /api/auto    │  │ AutoDeploy   │ │ (线程安全)         │ │
│  └──────┬───────┘  └──────────────┘  └────────────────────┘ │
│         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────┐│
│  │              PipelineEngine（编排引擎）                    ││
│  │  git_clone → branch_select → generate → git_push →       ││
│  │  ssh_connect → install_tool → configure_pipeline          ││
│  └──────┬──────────────────┬────────────────────────────────┘│
│         ▼                  ▼                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────────────┐ │
│  │  GitOps      │  │  SSHOps      │  │  配置生成器         │ │
│  │  clone/push  │  │  SSH/多跳    │  │  jenkins/github/    │ │
│  │  分支管理     │  │  堡垒机穿透   │  │  gitlab/aliyun/... │ │
│  └──────────────┘  └──────────────┘  └────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 分层职责

| 层级 | 组件 | 职责 |
|------|------|------|
| **表现层** | `frontend/src/views/MainView.vue` | 表单收集、校验、WebSocket 进度展示 |
| **API 层** | `backend/main.py` | Pydantic 模型定义、路由分发、WebSocket 管理 |
| **编排层** | `backend/pipeline/engine.py` | 步骤化执行引擎、进度推送、异常处理 |
| **操作层** | `pipeline/git_ops.py`、`pipeline/ssh_ops.py` | Git 仓库操作、SSH 远程执行 |
| **生成层** | `generators/*.py` | 按工具维度生成配置文件内容 |
| **存储层** | `pipeline/credential.py` | 线程安全的内存凭据管理 |

### 2.3 数据流

```
用户填写表单
    │
    ▼ POST /api/auto-deploy (AutoDeployConfig)
    │
    ├─ 1. Pydantic 校验 → 序列化 dict → 写入 CredentialStore
    │
    ├─ 2. 创建 PipelineEngine(config, credential_store)
    │
    ├─ 3. engine.run() 按 STEPS 顺序执行：
    │     ├─ git_clone:    克隆仓库到本地临时目录
    │     ├─ branch_select: 选择/创建目标分支
    │     ├─ generate:     调用生成器产出配置文件
    │     ├─ git_push:     推送配置文件到远程仓库
    │     ├─ ssh_connect:  SSH 连接目标服务器
    │     ├─ install_tool: 远程安装 CI/CD 工具
    │     └─ configure:    远程配置流水线 Job
    │
    └─ 4. 每步通过 WebSocket 推送进度 → 前端实时展示
```

## 3. 核心功能

### 3.1 一键生成配置文件

根据用户选择的项目类型和 CI/CD 工具，自动生成完整的配置文件集合：

| 项目类型 | 生成文件 |
|---------|---------|
| Java Maven | `pom.xml` + `Jenkinsfile` / `.gitlab-ci.yml` / `.github/workflows/*.yml` + `Dockerfile` + `docker-compose.yml` |
| Java Gradle | `build.gradle` + 流水线配置 + Docker 配置 |
| Node.js | `package.json` + 流水线配置 + `Dockerfile`（多阶段构建） |
| Python | `requirements.txt` + 流水线配置 + `Dockerfile` |
| Go | `go.mod` + 流水线配置 + `Dockerfile` |
| PHP | `composer.json` + 流水线配置 + `Dockerfile`（Nginx + PHP-FPM） |

### 3.2 一键自动搭建

完整的端到端自动化流程：

1. **Git 仓库克隆**：支持 HTTPS（密码注入）和 SSH（密钥临时文件）两种认证
2. **分支管理**：自动选择或创建目标分支
3. **配置文件生成**：根据项目类型 + 工具 + 部署模式生成全套文件
4. **Git 推送**：将生成的配置文件推送到远程仓库
5. **SSH 连接**：支持直连、中继跳转、堡垒机穿透、多跳链路
6. **工具安装**：远程安装 Jenkins / GitLab Runner / Docker 等
7. **流水线配置**：远程创建 Jenkins Job / 注册 Runner / 配置云效流水线

### 3.3 7 种 CI/CD 工具支持

#### Jenkins

- 自动生成 `Jenkinsfile`（声明式 Pipeline）
- 支持 Docker 容器化部署和直接部署
- 多分支并行构建（parallel stage）
- 发布审批与回滚机制
- 远程 Job 创建与配置

#### GitHub Actions

- 自动生成 `ci.yml`（构建测试）+ `deploy.yml`（部署）
- matrix 策略实现多分支并行构建
- workflow_run 触发器实现 CI→CD 串联
- 自动写入 Secrets（通过 PyNaCl 加密）
- Self-hosted Runner 支持

#### GitLab CI

- 自动生成 `.gitlab-ci.yml`
- YAML anchor 复用集成合并脚本
- 多分支通过 rules/only 控制
- Runner 自动注册与 tag 匹配
- Variables 管理敏感配置

#### 阿里云效 DevOps

- 通过 AccessKey 调用云效 OpenAPI
- 自动创建流水线、服务连接、变量组
- 支持区域选择（下拉列表，7 个常用区域）
- 支持组织 ID 配置

#### 华为云 CodeArts

- AccessKey 认证调用 CodeArts API
- 自动创建流水线项目
- 支持区域选择（6 个常用区域）

#### 腾讯云 CODING

- AccessKey 认证调用 CODING API
- 自动创建流水线
- 支持区域选择（6 个常用区域）

#### GitLab Runner（自托管）

- 自动生成 Runner 安装脚本
- `config.toml` 配置生成
- systemd 服务文件生成
- 支持 Docker / Shell 两种执行器

### 3.4 6 种项目类型适配

每种项目类型都有针对性的构建策略：

| 类型 | 构建命令 | 产物 | 特殊处理 |
|------|---------|------|---------|
| Java Maven | `mvn clean package` | `.jar` / `.war` | JDK 版本选择（8/11/17/21） |
| Java Gradle | `./gradlew build` | `.jar` / `.war` | JDK 版本选择 |
| Node.js | `npm run build` | `dist/` 静态文件 | Node 版本选择（18/20/22） |
| Python | `pip install -r requirements.txt` | 源码 | 虚拟环境管理 |
| Go | `go build` | 二进制文件 | CGO 配置 |
| PHP | `composer install` | 源码 | Nginx + PHP-FPM 配置 |

### 3.5 3 种部署模式

#### Docker 容器化部署

- 自动生成多阶段 `Dockerfile`
- `docker-compose.yml` 编排
- `.dockerignore` 排除无关文件
- 支持镜像构建、推送、容器重启

#### 直接部署

三种子模式：

| 子模式 | 说明 | 适用场景 |
|--------|------|---------|
| 含产物构建 | 先构建再部署（mvn package → scp jar） | 生产环境 |
| 纯代码部署 | 直接拉取源码运行 | 快速迭代/解释型语言 |
| 代码+依赖 | 打包代码+本地仓库整体传输 | 离线环境 |

#### 应用服务器部署

- 支持 Tomcat（Java WAR）
- 支持 Nginx（静态文件/PHP）
- 支持 Gunicorn/uWSGI（Python）

### 3.6 多环境部署

支持 dev / test / staging 等多环境独立部署：

```
environments:
  - name: dev
    branch: env/dev
    server: 10.1.0.1
  - name: test
    branch: env/test
    server: 10.1.0.2
```

- 每个环境有独立的分支和部署服务器
- Jenkins 通过 stage 级 `environment {}` 覆盖 SERVER_HOST
- GitHub 通过 job 级 `env` 覆盖
- GitLab 通过 job 级 `variables` 覆盖

### 3.7 两种流水线模式

#### Release 模式（发布合并）

```
feature → build/test → deploy → merge to main
```

- 测试通过后自动合并到主分支
- 适合稳定的生产发布流程

#### Integration 模式（临时集成测试）

```
feature → merge to env/dev (临时) → build/test → 不合并主干
```

- 将功能分支临时合入环境集成分支进行测试
- 合并不推送到远端，仅 CI 工作区内操作
- 冲突即中止，不影响主干代码
- 适合多团队并行开发的集成验证

### 3.8 负载均衡部署

#### Nginx 负载均衡

- 自动生成 `deploy/nginx-lb.conf`（upstream 配置）
- 自动生成 `deploy/rolling-deploy.sh`（滚动部署脚本）

#### 滚动部署

```
Server 1: 停止 → 部署新版本 → 健康检查 → 启动
Server 2: 停止 → 部署新版本 → 健康检查 → 启动
...
```

- 逐台部署，保证服务不中断
- 每台部署后执行 HTTP 健康检查（curl 重试 N 次，间隔 5 秒）
- 任一台失败即中止，保护存量服务

#### 引擎自动配置

- 自动连接所有 LB 后端服务器
- 自动安装 Nginx 并上传 upstream 配置
- 失败仅警告不阻断，提供手动配置指引

### 3.9 跨云/隔离网络部署

#### 中继服务器模式

```
CI/CD 服务器 → 中继服务器 → 目标服务器
```

- 中继服务器同时能访问 CI/CD 端和目标端
- SSH Transport 经中继建立隧道

#### 堡垒机穿透

```
CI/CD 服务器 → 堡垒机（ProxyJump） → 目标服务器
```

- 支持密码和 SSH 密钥两种认证
- 生成 Pipeline 中通过 `ssh -J` 穿透

#### 多跳链路

```
CI/CD → 零信任网关 → 堡垒机 → 目标服务器
```

- 支持任意跳数的网络链路配置
- 每跳独立认证方式

### 3.10 离线安装包兜底

三级降级安装策略：

1. **在线安装**：官方源 / 国内镜像（清华/阿里）
2. **离线兜底**：从 `bundled-tools/` 上传预置安装包
3. **手动提示**：安装失败时给出手动安装命令

覆盖组件：Jenkins WAR、OpenJDK 8/17、Docker、GitLab Runner

### 3.11 智能部署建议

根据用户选择自动分析并推荐：

- CI/CD 服务器部署位置（本地 vs 目标服务器 vs 独立服务器）
- Docker vs 直接部署
- 跨云/隔离网络方案
- 安全提示（凭据管理、网络隔离等）

### 3.12 实时进度反馈

- WebSocket 双向通信
- 每步骤实时推送进度百分比和日志
- 凭据缺失时暂停等待用户输入
- 错误时给出明确的修复建议

## 4. 技术特点与优势

### 4.1 核心优势

| 优势 | 说明 |
|------|------|
| **零门槛** | 无需学习任何 CI/CD DSL，表单填写即可 |
| **全覆盖** | 7 种工具 × 6 种项目类型 × 3 种部署模式，覆盖绝大多数场景 |
| **一键到底** | 从配置生成到远程部署全自动化，无需手动介入 |
| **跨云能力** | 内置中继/堡垒机/多跳链路，解决最复杂的网络场景 |
| **安全优先** | 凭据不落地、不落盘、不进生成物，内存存储 + 任务级隔离 |
| **离线可用** | 三级降级安装，断网环境也能完成部署 |
| **国产化支持** | 支持阿里云效、华为云 CodeArts、腾讯云 CODING |
| **桌面应用** | 支持 macOS/Windows/Linux 桌面版，开箱即用 |

### 4.2 技术亮点

#### 无状态架构

- 所有配置仅存在于单次请求和进程内存中
- 无数据库、无配置文件、无持久化依赖
- 重启即恢复初始状态，天然幂等

#### 步骤化编排引擎

```python
STEPS = [
    ("git_clone",        "克隆仓库"),
    ("branch_select",    "选择分支"),
    ("generate_config",  "生成配置"),
    ("git_push",         "推送配置"),
    ("ssh_connect",      "连接服务器"),
    ("install_tool",     "安装工具"),
    ("configure_pipeline","配置流水线"),
]
```

- 每个步骤独立、可重试
- 步骤间通过引擎属性传递状态
- 异常时精确定位失败步骤

#### 凭据按需请求

```
步骤执行 → 检测凭据缺失 → WebSocket 弹窗请求 → 用户输入 → 写入 CredentialStore → 继续执行
```

- 不在初始表单中强制收集所有凭据
- 按需请求，减少用户认知负担
- 凭据仅存内存，任务结束自动清理

#### 生成器与引擎解耦

- 生成器（`generators/*.py`）仅负责文件内容输出，无网络 I/O
- 引擎（`pipeline/engine.py`）负责编排和网络操作
- 新增工具只需实现生成器，无需修改引擎

#### YAML Anchor 复用（GitLab）

```yaml
.integration_merge: &integration_merge |-
  if [ "$CI_COMMIT_BRANCH" != "env/dev" ]; then
    git merge "$CI_COMMIT_BRANCH" --no-edit
  fi

test:
  before_script:
    - *integration_merge
```

- 每个 job 独立容器，需要独立执行合并逻辑
- 通过 YAML anchor 避免重复定义

| 特性 | 本平台 | Jenkins 原生 | GitLab CI | GitHub Actions |
|------|--------|-------------|-----------|----------------|
| 多工具支持 | ✅ 7 种 | ❌ 仅 Jenkins | ❌ 仅 GitLab | ❌ 仅 GitHub |

## 5. 使用指南

### 5.1 环境要求

| 组件 | 最低版本 | 推荐版本 |
|------|---------|---------|
| Python | 3.9 | 3.11+ |
| Node.js | 18 | 22 LTS |
| npm | 9 | 10+ |
| 操作系统 | macOS / Linux / Windows | macOS / Linux |

### 5.2 安装与启动

#### 方式一：开发模式

```bash
# 1. 克隆仓库
git clone <repo-url>
cd auto-cicd

# 2. 安装后端依赖
cd backend
pip3 install -r ../requirements.txt

# 3. 安装前端依赖
cd ../frontend
npm install

# 4. 启动后端（端口 8000）
cd ../backend
python3 -m uvicorn main:app --host 0.0.0.0 --port 8000
# 或直接
python3 main.py

# 5. 启动前端（端口 3000，另开终端）
cd frontend
npm run dev
```

访问 `http://localhost:3000` 即可使用。

#### 方式二：生产模式（统一服务）

```bash
# 1. 构建前端
cd frontend
npm run build    # 产物输出到 frontend/dist/

# 2. 启动统一服务（同时提供 API 和前端静态文件）
cd ../backend
python3 standalone.py
# 默认监听 0.0.0.0:8000
# 可通过环境变量覆盖：PORT=9000 HOST=127.0.0.1 python3 standalone.py
```

访问 `http://localhost:8000` 即可使用。

#### 方式三：桌面应用

```bash
# macOS / Linux
./build-desktop.sh

# Windows
build-desktop.bat
```

构建产物位于 `dist/` 目录：
- macOS: `dist/AutoCICD.app`
- Linux: `dist/AutoCICD` 或 `.deb` / `.AppImage`
- Windows: `dist/AutoCICD.exe`

#### 方式四：Docker 部署

## 7. 部署模式详解

### 7.1 Docker 容器化部署

**适用场景**：生产环境、微服务架构、需要环境一致性

**生成文件**：
- `Dockerfile`：多阶段构建（构建阶段 + 运行阶段）
- `docker-compose.yml`：容器编排
- `.dockerignore`：排除无关文件

**流程**：
```
代码 → 构建镜像 → 推送镜像仓库 → 目标服务器拉取 → 启动容器
```

**示例（Java Maven）**：
```dockerfile
# 构建阶段
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# 运行阶段
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

### 7.2 直接部署 — 含产物构建

**适用场景**：生产环境、不需要容器化的场景

**流程**：
```
代码 → 构建（mvn package）→ scp 产物到目标 → 停止旧服务 → 启动新服务
```

**生成的 Pipeline 关键步骤**：
1. `mvn clean package -DskipTests`
2. `scp target/*.jar user@server:/opt/project/`
3. `ssh user@server "pkill -f app.jar || true"`
4. `ssh user@server "nohup java -jar /opt/project/app.jar &"`

### 7.3 直接部署 — 纯代码部署

**适用场景**：Python/Node.js 等解释型语言、快速迭代

**流程**：
```
代码 → scp 源码到目标 → 安装依赖 → 启动服务
```

### 7.4 直接部署 — 代码+依赖

**适用场景**：离线环境、依赖同步困难

**流程**：
```
代码 + 本地仓库（.m2/node_modules）→ 打包 tar.gz → scp 到目标 → 解压 → 启动
```

### 7.5 应用服务器部署

**适用场景**：传统 Java Web 应用（Tomcat）、PHP 应用（Nginx）

**Tomcat 部署**：
```
代码 → mvn package → scp .war 到 Tomcat webapps/ → 自动解压部署
```

**Nginx 部署**：
```
代码 → npm run build → scp dist/ 到 Nginx 目录 → reload Nginx
```

## 8. 高级特性

### 8.1 多分支并行构建

当 `branches` 包含多个分支时，自动生成并行构建配置：

**Jenkins**：
```groovy
stage('Parallel Build') {
    parallel {
        stage('main') { /* ... */ }
        stage('develop') { /* ... */ }
    }
}
```

**GitHub Actions**：
```yaml
strategy:
  matrix:
    branch: [main, develop]
```

**GitLab CI**：
```yaml
build-main:
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

build-develop:
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
```

### 8.2 发布策略

| 策略 | 说明 |
|------|------|
| `auto_merge` | 测试通过后自动合并到主分支 |
| `manual_merge` | 审批通过后手动合并 |
| `no_merge` | 仅测试不合并 |

### 8.3 集成测试模式详解

**Release 模式**（默认）：
```
feature 分支 → CI 构建测试 → 部署到生产 → 合并到 main
```

**Integration 模式**：
```
feature 分支 → 临时合入 env/dev → CI 构建测试 → 不合入 main
```

集成模式的关键行为：
- 合并在 CI 工作区本地执行，**不推送到远端**
- 冲突时立即中止，输出冲突详情
- 目标环境 = `environments[0]`（第一个环境）
- Jenkins 通过 `when { not { branch env_branch } }` 控制触发条件
- GitHub 通过 `if: github.ref_name != env_branch` 控制
- GitLab 通过 shell 脚本 `if [ "$CI_COMMIT_BRANCH" != "env/dev" ]` 控制

### 8.4 负载均衡部署详解

#### 滚动部署脚本

```bash
#!/bin/bash
# deploy/rolling-deploy.sh

SERVERS=("10.0.0.11" "10.0.0.12" "10.0.0.13")
HEALTH_CHECK_PATH="/health"
HEALTH_CHECK_RETRIES=6
HEALTH_CHECK_INTERVAL=5

for SERVER in "${SERVERS[@]}"; do
    echo ">>> 部署到 $SERVER"

    # 1. 停止旧服务
    ssh $SERVER "systemctl stop myapp || true"

    # 2. 上传新版本
    scp myapp-artifact.tar.gz $SERVER:/opt/myapp/
    ssh $SERVER "cd /opt/myapp && tar xzf myapp-artifact.tar.gz"

    # 3. 启动新服务
    ssh $SERVER "systemctl start myapp"

    # 4. 健康检查
    for i in $(seq 1 $HEALTH_CHECK_RETRIES); do
        if curl -sf "http://$SERVER:8080$HEALTH_CHECK_PATH" > /dev/null; then
            echo "✅ $SERVER 健康检查通过"
            break
        fi
        if [ $i -eq $HEALTH_CHECK_RETRIES ]; then
            echo "❌ $SERVER 健康检查失败，中止部署"
            exit 1
        fi
        sleep $HEALTH_CHECK_INTERVAL
    done
done
```

## 9. 安全与最佳实践

### 9.1 凭据安全

| 原则 | 实现 |
|------|------|
| **凭据不落地** | 仅存于内存 `CredentialStore`，进程退出即清除 |
| **凭据不进生成物** | Jenkinsfile / YAML / Shell 中不含任何密码明文 |
| **任务级隔离** | 凭据按 `task_id` 隔离，不同任务互不可见 |
| **按需请求** | 仅在步骤执行到需要时才弹窗请求，减少暴露面 |
| **加密传输** | GitHub Secrets 通过 PyNaCl（libsodium）加密后写入 |

### 9.2 网络安全

- SSH 连接支持密钥认证（推荐替代密码）
- 堡垒机穿透避免直接暴露内网服务器
- 生成的 `.gitignore` 排除 `.env` 文件
- WebSocket 连接通过 task_id 鉴权

### 9.3 最佳实践

#### 凭据管理

- 生产环境使用 SSH 密钥而非密码
- 云服务使用 RAM/IAM 子账号，遵循最小权限原则
- 定期轮换 AccessKey

#### 网络配置

- 跨云部署务必配置中继服务器
- 隔离网络使用多跳链路
- 堡垒机启用密钥认证 + 二次验证

#### 部署策略

- 生产环境使用 Docker 部署，保证环境一致性
- 多环境部署使用 Integration 模式做集成验证
- 负载均衡场景启用滚动部署 + 健康检查

#### 离线环境

- 提前执行 `download-bundled-tools.sh --all` 下载离线包
- 桌面版构建时设置 `INCLUDE_BUNDLED_TOOLS=1`
- 配置国内镜像源加速在线安装

### 9.4 注意事项

- 项目名/分支名/环境名会插值进生成的 Shell 和 YAML 文件。当前输入源为平台使用者本人，但若未来开放多租户，需对插值字段做白名单校验
- Jenkins 集成阶段已包含 `git config user.name/email`，确保 merge 命令可执行
- GitHub 集成模式手动触发时，checkout 回退到 `github.ref_name`
- GitHub/GitLab 的多环境远程部署仅支持 Docker 模式（直接部署在 runner 本地运行，无远程部署能力）

## 11. 已知边界与限制

| 边界 | 说明 |
|------|------|
| Jenkins 多分支并行模式 | `branches > 1` 时走独立的 multibranch 模板，不叠加 LB/多环境/集成能力 |
| 云效/CodeArts/CODING | 生成器未适配 LB/多环境/集成模式（其流水线结构由云平台决定） |
| GitHub/GitLab 多环境直接部署 | direct 模式在 runner 本地运行，仅 Docker 模式支持多环境远程部署 |
| LB 健康检查端口 | 取应用 `port` 字段，若后端服务端口与 LB 端口不同需手动调整 |
| 集成模式目标环境 | 固定为 `environments[0]`（第一个环境） |
| 版本号管理 | spec / package.json / Linux 打包脚本中的版本号需手动同步 |
| 无持久化 | 所有配置仅存于内存，重启后丢失 |

### Q2: Docker 部署 vs 直接部署怎么选？

- **Docker 部署**：推荐生产环境，环境一致性、易于迁移、支持多环境远程部署
- **直接部署**：适合轻量级场景、已有运行环境、不需要容器化

### Q3: 跨云部署如何配置？

1. 配置中继服务器（同时能访问 CI/CD 端和目标端）
2. 或配置堡垒机穿透（SSH ProxyJump）
3. 或配置多跳链路（零信任网关 + 堡垒机）

### Q4: 离线环境如何部署？

1. 在有网环境执行 `download-bundled-tools.sh --all` 下载离线包
2. 将 `bundled-tools/` 目录拷贝到离线环境
3. 构建时设置 `INCLUDE_BUNDLED_TOOLS=1` 将离线包打入可执行文件
4. 运行时自动检测并使用离线包安装

### Q5: 如何添加新的 CI/CD 工具支持？

1. 在 `backend/generators/` 下创建新文件（如 `bitbucket.py`）
2. 实现 `generate_xxx(config, output_dir)` 函数，返回文件列表
3. 在 `backend/main.py` 中注册工具映射
4. 前端 `tools` 数组中添加新工具选项

### Q6: 凭据泄露了怎么办？

- 凭据仅存于进程内存，重启后端即清除
- 生成的配置文件中不含密码明文
- 若怀疑泄露，立即轮换相关凭据（密码/AccessKey/SSH 密钥）

### Q7: 如何自定义生成的配置文件？

- 生成文件输出到 `output/<projectName>_<tool>_<timestamp>/`
- 可直接编辑生成的文件
- 或 Fork 项目修改 `generators/*.py` 中的模板

### Q8: 支持 Windows 目标服务器吗？

- 后端支持在 Windows 上运行（需 Python 3.9+）
- 目标服务器目前仅支持 Linux（SSH 部署）
- Windows 目标服务器需要额外适配（WinRM 等）
